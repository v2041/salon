# Доменные документы

Правила чтения доменной документации для инженерных скиллов.

## Перед исследованием прочитайте

- **`GLOSSARY.md`** в корне репозитория, или
- **`GLOSSARY-MAP.md`** в корне, если файл есть. Он указывает на `GLOSSARY.md` каждого контекста. Прочитайте нужные контексты.
- **`docs/adr/`**: прочитайте ADR, которые касаются вашей области.

Если файлов нет, работайте дальше молча. Не сообщайте об их отсутствии и не предлагайте создать их заранее. Скилл `/domain-modeling` (через `/grill-with-docs` и `/improve-codebase-architecture`) создаёт их лениво, когда термины или решения действительно появляются.

## Структура файлов

Репозиторий с одним контекстом (как этот):

```
/
├── GLOSSARY.md
├── docs/adr/
├── backend/
└── frontend/
```

Репозиторий с несколькими контекстами (есть `GLOSSARY-MAP.md` в корне):

```
/
├── GLOSSARY-MAP.md
├── docs/adr/
└── src/
    ├── ordering/
    │   ├── GLOSSARY.md
    │   └── docs/adr/
    └── billing/
        ├── GLOSSARY.md
        └── docs/adr/
```

## Используйте словарь глоссария

Когда вывод называет доменное понятие (заголовок issue, предложение рефакторинга, гипотеза, имя теста), используйте термин из `GLOSSARY.md`. Не заменяйте его синонимами, которые глоссарий избегает.

Если понятия нет в глоссарии, это сигнал. Либо вы вводите язык, которого нет в проекте (пересмотрите), либо есть реальный пробел (отметьте для `/domain-modeling`).

## Сообщайте о конфликтах с ADR

Если вывод противоречит существующему ADR, скажите об этом явно. Не переопределяйте решение молча.
